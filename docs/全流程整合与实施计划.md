## 三、四个地基问题（会改变流程设计）

### ★A：多章的地基现在是坏的

`_extract_scenes(cfg, chapter_text, …)` 只收本章正文（`plan.py:764`），`save_scenes` **整表覆写** `scenes.json`（`plan.py:810`）→ **跑第二章就把第一章场景全部冲掉**。道具同理（`plan.py:621`/`:661`）。

更糟的是 ID：`S{i}`/`P{i}` 每章从 1 重编，**同一编号跨章指向不同地点**。实测 `projects/雨夜地铁/` 两章的 `scenes.json` 都只有 `S1/S2`，现存的 `S1` 是第二章的「站台」，第一章原本的 `S1`「末班地铁车厢」已丢失 → `vm/audit/completeness.py:197` 会据此误判「scene_id 不存在」。

> **章节管理 UI 建在这上面，只会让错误更隐蔽。** 必须先修。

### ★B：风格必须放在拆镜**之前**，不能像设想里排在第 4 步

风格句会被**烘进每一镜的 prompt 文本**——实测 `shots/chapter01.json` 第 1 镜 `detailed_description` 开头就是 `Gritty cinematic realism, cold cyan-grey palette…`。拆完再改风格 = 全部提示词重写 = 全部重渲（52 镜 ≈ 36 分钟 GPU）。

**风格应当是拆镜的前置门禁**，而不是拆镜的下游选项。

### ★C：现在改风格，什么都不失效

- 镜头指纹只含 `prompt/chars/refs/unet/lora/steps/w/h/frames/seed`（`state.py:84-97`），**没有风格项**
- `config.py:403` 自己就写着 `stale="不影响已有镜头（风格句已固化在提示词里）"`
- 定妆照**根本没有指纹机制**：`chars.py:255-257` 见 `refs/char_X.png` 存在就跳过

叠加 README 的实测局限「**画风由参考图决定，文字控不住**」——唯一有效的换风格通路是**重出参考图**，而它现在既不自动、也不提示要重出 = 换完就是新旧风格混存。

### ★D：单章增量拆镜是死路径

`--chapter` 参数定义了（`pipeline.py:564`）、worker 也认（`pipeline.py:484`），但 `_build_cmd` 从不拼它（`taskctl.py:4054-4076` 只有 `--only/--count/--force/--dry-run/--_fake-sleep`），Web 的 `_start` 也不收（`web.py:1402-1439`）。

**后果：改了 / 新增一章，要全部章节重跑一遍 LLM。** 章节管理一上线，这个立刻成为最痛的点。

### 另两处（P0 顺手修）

- ★实锤 **`assets.py:181` NameError**：`_st.negative_for(params.get("style_preset")) if isinstance(params, dict)` —— `params` 在 `gen_candidates(proj, kind, aid, *, n, force, log)` 的作用域内**不存在**（AST 核验确认），且全局仅这一处命中 → **场景/道具抽卡必崩**。
- **中文序数排序错**：`sorted(novel/*.md)` 按 Unicode 码位排 → 实测得「第一章, 第三章, 第二章, 第十章, 第四章」（`taskctl.py:2466`、`pipeline.py:84`）。于是 `--chapter N` 取的第 N 个 ≠「第 N 章」，`chapter_table` 的 `index` 与 `no` 也会分叉。

## 四、优化后的流程

```
① 新建项目       名字 + 来源类型(小说/剧本) + 一句话题材                    [新]
       │
② 章节管理       导入 .md/.txt（可多文件一次导）/ 手动粘贴编辑              [新]
       │         → chapters.json：显式顺序与元信息        ★不再靠文件名 sorted()
       │
③ 通读登记 ★★    一次 LLM 通读全书：                                        [新阶段]
       │           · 实体登记表（角色/场景/道具，项目级累积、跨章去重）
       │           · 推荐 style_preset + 整本级风格句
       │         ── 门禁 ──  用户在 UI 上确认或改风格，之后才允许拆镜    ★
       │
④ 定妆 & 概念图  按已确认风格出图：角色定妆 + 场景 + 道具，抽卡 → 采纳        [改] 风格真进图
       │         （可选：章节级造型变体，见 P3）
       │
⑤ 逐章拆镜       角色身份已由参考图锁定，只写动作/运镜/台词；支持单章增量      [改]
       │
⑥ 分镜图预演     （已有，可选）
⑦ 渲染 → ⑧ 质检 → ⑨ 合成                                                   [已有]
```

### 相对原设想的四处改动及理由

**1. 把「实体登记 + 风格」从拆镜里拆出来，提到最前面（新 `register` 阶段）**
原设想第 3 步「拆镜时搜集角色/场景/道具」方向是对的，但实现上**混在一次调用里正是 §3A 的根因**：实体是**全书级**的、拆镜是**逐章**的，两种生命周期塞进一次 LLM 调用，就成了每章重画一遍实体表并互相覆盖。拆开之后：登记跑一次（整本级）、拆镜逐章跑（只引用已登记的实体）。成本上只是**多一次很便宜的 LLM 调用**（现状一章约 1700 tokens）。

**2. 风格从「拆镜的产物」变成「拆镜的前置门禁」**
理由见 §3B。这是流程顺序上的实质改动：**先定风格，再拆镜**，避免改风格导致全表重渲。

**3. 定妆在拆镜之前**
README 踩过「文字外貌会压过参考图」的坑（实测结论）。先锁身份再拆镜，拆镜时可用的角色列表就是已定妆那批，`plan` 的 `locked` 机制天然成立，从源头断掉让 LLM 重写外貌。

**4. 「每章可能有变化」不做成"每章一套图"，做成「出现表 + 造型变体」**
每章重出全部角色 = 成本失控（实测两章 27+13 镜）。改为：默认全局一张；**只有 LLM 判定本章造型真变了**（换装 / 受伤 / 年龄 / 回忆梦境）才建 variant，variant 挂章节作用域、镜头级可覆盖。现成的 `costumes.json` variants + `shot.costume` 已经是这个形状，只差没接章节维度。

> ### ★★ 阻塞项：Qwen-Image **2.1** 通路在本机跑不通 → **已解决（2026-09-27 21:19）**
>
> 用户明示授权重启 ComfyUI 后修通。**根因不是"没装 nvrtc"**，而是 **soname 与 RUNPATH 目录错配**：
>
> | 事实 | 证据 |
> |---|---|
> | 报错的是 **KSampler 里的融合 attention**（`Matmul…EXP…Div…Matmul` = SDPA），不是文本编码器 | `/history` 的 `node_type: KSampler` |
> | 需要 JIT：RTX 5090（报错里 `smVersion:1200`）上 cuDNN 对这条 pattern **没有预编译 engine config** ⇒ 走 runtime-compile ⇒ 要 NVRTC | 报错首行 `No valid engine configs …` + `this->libnvrtc == nullptr` |
> | 磁盘上的 cuDNN 是 **cu13 构建**，它 dlopen 的是 `libnvrtc.so.13` | `strings nvidia/cudnn/lib/libcudnn_engines_precompiled.so.9` |
> | 但它的 **RUNPATH 只指到 `../../cuda_nvrtc/lib`**，那里只有 **12.8 的 `libnvrtc.so.12`**（`nvidia_cuda_nvrtc_cu12`）；`.so.13` 在 `nvidia/cu13/lib`，**不在 RUNPATH 里** | `readelf -d` 的 RUNPATH + 两个目录的文件清单 |
> | 进程 `LD_LIBRARY_PATH` 为空、`ldconfig` 缓存里没有 nvrtc ⇒ 按 soname 就是找不到（torch 是用绝对路径把 12.8 载进去的，所以它在内存里但"按名字找不到"） | `/proc/<pid>/environ`、`ldconfig -p` |
>

### 6.1 现状诊断：前端有和 `taskctl.py` 一模一样的病

`web/src` 共 **7771 行 / 33 个文件**。结构是**单屏四栏工作台 + 右栏 9 个平铺 tab**：


| 问题 | 证据 | 后果 |

### 6.2 重构原则（这条比任务清单重要）

> **只把「低频 · 项目级 · 镜头存在之前」的东西分屏；「高频 · 审片循环」一律留在工作台内。**

现在这块四栏工作台对「镜头表 ↔ 质检 ↔ 日志 ↔ 成片」这个高频循环是**真的好**——一眼看全、不用切屏，这正是 README 立的"每一步都能看、能改、能重来，不是黑盒"的界面体现（`README.md:4`）。多屏化如果把这个优点做没了，是负优化。

因此四条硬约束：
1. **工作台仍是默认落地屏，形状不动**，`ui-e2e.mjs` 97 项**不重写**（只允许新增用例）。
2. 分出去的只有 `章节` 与 `实体+风格` 两块**前置**界面。
3. 从右栏**提出**来的只有 `成片`（它自带播放器 + 分段条 + 胶片条，挤在 420px 里本就委屈）。
4. 右栏 tab 从 9 个**减到 ≤7**，不是变多。

### 6.3 目标形态：导航即流程

```
壳  TopBar（项目 · 工作区切换 · 全局任务态）+ QueueFab + UiToggles + 全局错误条
│
├ W0 项目        项目卡片墙 + ➕ 新建向导                        [新 ← P1.1/P1.4]
├ W1 章节        列表(状态徽标) + 正文编辑 + 导入对话框            [新 ← P1.2/P1.3]
├ W2 实体与风格   风格门禁面板 + 角色/场景/道具总表(可手工合并拆分)   [新 ← P2.5/P3.1]
├ W3 镜头工作台   ★现状整体原样收进来：四栏 + 右栏 ≤7 tab + 胶片条   [保留 = 默认屏]
└ W4 成片与审片   播放器 + 分段条 + 质检 + 审计 同屏联动             [从右栏提出]
```

W0→W1→W2→W3→W4 就是 §四 的流程顺序。但**不做强制向导**——不许出现"下一步"按钮把用户锁死在某一屏；老用户直达 W3、任意屏可回，这是"每一步都能重来"在导航层的体现。

**两个技术选型（需要拍板，见 §8 未决问题）**：
- 屏的表达：引入 `vue-router`（+1 依赖、+2KB）还是 **~60 行 hash 视图切换**（`#/w3?shot=1-2-03`）。倾向后者——本机单人工具，只需要"可分享、可回退"，不需要嵌套路由/守卫。
- store 拆分：**用起已装的 pinia**（`defineStore` 按域切 6 个），不再手写 reactive module。零新增依赖。

### 10.2 明确不加

### 10.3 ★ 后端不要"顺手优化"成 FastAPI

`CONTRACTS.md:32` 硬约束 #5 明写**后端零第三方依赖（只用标准库 + ffmpeg）**，这是 Lead 定的纪律，收益是真的：README「开始用」只有 4 行，`python3 pipeline.py --serve` 装都不用装。

但你要知道"少手搓"的收益大头其实在后面而不在前面 —— 实测规模：

| 后端手搓项 | 规模 | 框架能省 |
|---|---|---|
| `taskctl.py` | **4307 行 / 147 函数 ≈ 10 个子系统** | FastAPI 省不了，这是业务不是框架 |
| `web.py` | 1517 行 / **49 个端点**手工登记在两张路由表 | 校验+序列化+路由+文档，约砍一半 |
| `config.py` | 1235 行手写 schema 校验与三段说明 | pydantic 天然干这个 |
| `wsclient.py` | **261 行手搓 WebSocket 客户端（自己拼帧）** | `websocket-client` 一行 |

**本期维持现状。** 只记一条：哪天要做成多人用的产品，FastAPI 化是第一步，而且 `config.py` 的 SCHEMA 设计得干净、能原样变成 pydantic model，是条通得了的路。

### 10.4 这条决策改变了什么

- §8 的 **D1 我改口**：原倾向"~60 行手搓 hash 切换"，改为**用 vue-router** —— 因为实测发现项目**连路由都没有**，那 60 行会长成"自己的小路由"，而 `<KeepAlive>` 保屏内状态 + `scrollBehavior` 是白送的。
- **F0.1 的做法确定**：pinia，不是手工 reactive module。
- **F0.2 的产物变了**：从"手搓 `useTicker`"变成"接 vue-query 并把手搓的三份轮询迁进去"。工作量没减多少，但删掉的代码比新写的多，且顺带解决 §8 风险 7（无 SSE 时的数据闪变）。
- **F 系列总工期不变**（7–7.5 天），因为 F0.1 从"拆 667 行"变成"拆 667 行 + 学 pinia"，而 pinia 已经在依赖里、概念只有 `state/getters/actions` 三个。
